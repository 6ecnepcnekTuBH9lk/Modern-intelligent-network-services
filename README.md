REST API сервиса агроскоринга для дисциплины «Современные интеллектуальные сетевые сервисы».

Основной источник требований — `Практическая_работа_1_Совр_Инт_Сет_Сер.pdf`.
Дополнительный эталон — [main.py преподавателя](https://gitverse.ru/MKornet/AI_services/content/master/%D0%9B%D0%B0%D0%B1%D0%BE%D1%80%D0%B0%D1%82%D0%BE%D1%80%D0%BD%D1%8B%D0%B5%20%D1%80%D0%B0%D0%B1%D0%BE%D1%82%D1%8B/1/main.py).

## Обработка прогноза

Поток обработки: JSON → Pydantic → проверка готовности модели → бизнес-валидация региона →
`calculate_risk` → категория и рекомендация → UUID → сохранение в словарь → JSON-ответ.

Все девять полей `FarmRequest` обязательны. Строки `farm_id`, `region`, `crop_type` не могут
быть пустыми; `area_ha > 0`; `temperature_avg` находится в диапазоне от −60 до 60 включительно;
осадки, дни просрочки, число дефолтов и долг неотрицательны. Допустимые регионы проверяются
отдельно: `Krasnodar`, `Rostov`, `Stavropol`.

Алгоритм преподавателя:

| Условие | Вклад в риск |
|---|---:|
| Базовая оценка | 0.1 |
| `payment_delay_days > 30` | +0.3 |
| `previous_defaults > 0` | +0.3 |
| `debt > 5_000_000` | +0.2 |
| `precipitation_mm < 100` | +0.1 |

Результат ограничивается сверху значением 1.0 и округляется до двух знаков, как в коде
преподавателя. Категории: `< 0.3` — `low`, `< 0.7` — `medium`, иначе — `high`.

Рекомендации:

- `low`: «Стандартное рассмотрение»;
- `medium`: «Требуется дополнительная проверка»;
- `high`: «Высокий риск. Требуется ручное рассмотрение».

Пример тела `POST /predict` из методички:

```json
{
  "farm_id": "FARM-001",
  "region": "Krasnodar",
  "crop_type": "wheat",
  "area_ha": 2500,
  "temperature_avg": 24.3,
  "precipitation_mm": 320,
  "payment_delay_days": 45,
  "previous_defaults": 1,
  "debt": 6500000
}
```

Для этого запроса возвращается `risk_score=0.9`, `risk_level=high`, рекомендация о ручном
рассмотрении, `model_version="1.0"`, `farm_id` и новый UUID версии 4 в `request_id`.

## API-контракт

| Метод и endpoint | Вход | Ответ | Успех | Ожидаемые ошибки |
|---|---|---|---:|---|
| `GET /health` | — | `HealthResponse`: `status=ok` | 200 | — |
| `GET /model-info` | — | `ModelInfoResponse`: название, версия, тип, готовность модели | 200 | — |
| `POST /predict` | JSON `FarmRequest` | `PredictionResponse` | 200 | 400, 422, 503 |
| `GET /predictions/{request_id}` | строковый path-параметр | `PredictionResponse` | 200 | 404 |
| `GET /predictions` | `limit`, необязательный `risk_level` | список `PredictionResponse` | 200 | 400, 422 |

`limit` по умолчанию равен 10, допустимый диапазон — 1…100. Фильтр принимает `low`, `medium`,
`high`; другое значение возвращает 400, как у преподавателя. Сначала применяется фильтр,
затем ограничение количества. Прогнозы возвращаются в порядке добавления, как в исходном
`values[:limit]`; повторный запрос хозяйства создаёт новый прогноз с новым UUID.

Методичка допускает 200/201 для успешного прогноза; в эталоне преподавателя явно установлен
200, поэтому здесь выбран 200. Дополнительные ограничения строк и температуры,
тексты рекомендаций, округление оценки и проверка фильтра взяты из эталона.

`MODEL_READY = True` находится в `main.py`. Если изменить его на `False` и перезапустить
приложение, корректный `POST /predict` вернёт 503 с `detail="Model is temporarily unavailable"`,
а `/model-info` — `status="unavailable"`. `/health` продолжает отвечать `status="ok"`:
работоспособность HTTP-сервиса и готовность модели проверяются отдельно. Структурно неверное
тело всё равно даёт 422 ещё до вызова endpoint; для корректного тела проверка готовности
предшествует бизнес-валидации региона.

Каждый обработанный запрос получает заголовок `X-Process-Time` со временем обработки
в секундах. В лог пишутся метод, путь, код ответа, длительность, идентификаторы прогнозов,
версия модели и результат оценки. Необработанные исключения записываются со стеком.

Результаты хранятся в памяти одного процесса и исчезают после его перезапуска, в том числе
при автоматическом перезапуске с `--reload` после изменения исходников.

## Проведённые проверки

Проверено 05.10.2026. Все запросы выполнялись по HTTP к реально запущенному uvicorn.
Для проверки 503 запускался отдельный процесс с `main.MODEL_READY=False`.

| Проверка | Полученный HTTP-код | Результат |
|---|---:|---|
| `GET /health` | 200 | `status=ok` |
| `GET /model-info` | 200 | Метаданные и `status=ready` |
| Корректный `POST /predict` | 200 | UUID, оценка, категория, рекомендация |
| `POST /predict`, `area_ha=-100` | 422 | Ошибка поля `area_ha` |
| `POST /predict`, неизвестный регион | 400 | Список допустимых регионов в `detail` |
| Получение существующего `request_id` | 200 | Сохранённый результат совпадает с ответом `/predict` |
| Получение неизвестного `request_id` | 404 | `Prediction not found` |
| `GET /predictions?limit=2` | 200 | Два первых результата |
| `GET /predictions?risk_level=high` | 200 | Только прогнозы высокого риска |
| `GET /predictions?limit=-5` | 422 | Ошибка query-параметра `limit` |
| `GET /docs` | 200 | HTML Swagger UI |
| `GET /openapi.json` | 200 | Все пять endpoints, схемы и коды ошибок |
| `risk_level=critical` | 400 | Недопустимая категория риска |
| `limit=0`, `limit=101`, `limit=abc` | 422 | Ошибки диапазона и типа |
| `limit=1`, `limit=100` | 200 | Допустимые границы |
| `risk_level=medium&limit=5` | 200 | Фильтр и лимит работают совместно |
| Отрицательные числовые поля, неверные типы, пустые строки, пропущенное поле | 422 | Хранилище не изменяется |
| Границы алгоритма: 30/31 день, долг 5 млн, осадки 100 мм, категории 0.3/0.7 | 200 | Ожидаемые оценки и категории |
| Регионы `Rostov`, `Stavropol` | 200 | Допустимые регионы принимаются |
| `POST /predict` при `MODEL_READY=False` | 503 | Прогноз не создаётся |
| `/health`, `/model-info` при неготовой модели | 200 | API работает, модель `unavailable` |

Дополнительно проверен настоящий браузер Edge: Swagger UI отображает все пять endpoints;
через `Try it out` / `Execute` отправлен пример из методички и получен HTTP 200 с риском 0.9
и категорией `high`. `pip check` сообщает `No broken requirements found`.
